# 06 · Demo Scenarios

Four scenarios. Each is a saved input loadable from a dropdown on the submit screen — no typing during the demo.

> **Sample data note.** The GSTIN literals below are illustrative and are written as `29ABCFS1234K1Z3`. The PAN is `ABCFS1234K`: its **4th character** is `F` (Firm/LLP), which is what R07 reads — not the trailing `K`. EC-4's PAN differs from the GSTIN-embedded one in the **last** character only, so R06 fires while R07 still sees a Firm/LLP code. Real sample fixtures are generated using `rules.gstin_checksum()` so that the 15th character is genuinely valid — otherwise R04 would fire in every scenario and mask the intended findings. **Never hand-write a GSTIN into a fixture.**

> **Sample document note.** The five PDFs in `samples/pdfs/` are generated by `samples/make_pdfs.py`, and every one of them carries a heading its real issuer would use — `PERMANENT ACCOUNT NUMBER CARD`, `FORM GST REG-06`, `CERTIFICATE OF INCORPORATION`, `BANK ACCOUNT CONFIRMATION LETTER`, `ELECTRICITY BILL — TAX INVOICE`. That is not decoration: R13 matches what the document calls itself against the slot it was uploaded into, so a fixture with a vague heading would fire R13 in every scenario for no reason.

## EC-1 · Happy path — **APPROVED**

**Vendor:** `Sundaram Industrial Supplies LLP`

| Field | Value |
|---|---|
| entity_type | `LLP` |
| country_of_incorporation | `IN` |
| registered_address | `42 Industrial Layout, Koramangala, Bengaluru` |
| registered_address_state | `Karnataka` |
| tax_id_type / gstin | `GSTIN` / `29ABCFS1234K1Z3` (checksum computed) |
| pan | `ABCFS1234K` |
| account_holder_name | `Sundaram Industrial Supplies LLP` |
| ifsc | `HDFC0001234` |
| documents | all 5 attached, each readable and in the right slot |

**Internal consistency:** state code `29` = Karnataka ✓ · embedded PAN `ABCFS1234K` = submitted PAN ✓ · PAN 4th character `F` = Firm/LLP = declared `LLP` ✓ · bank holder name = entity name ✓

**Document consistency:** PAN on the card = submitted PAN ✓ · GSTIN on the certificate = submitted GSTIN, and its embedded PAN = submitted PAN ✓ · LLPIN `AAB-1234` is a well-formed LLPIN for an LLP ✓ · the electricity bill is addressed to the entity, in Karnataka ✓

The street address on the bill sits beside the submitted `registered_address` in the comparison
panel and is **not** compared — see `10-assumptions-and-scope.md`. On this scenario the two happen
to read the same, which is a fact about the fixture and not a check that passed.

**Rules triggered:** none. All 17 pass.

**Status:** `APPROVED`

**Output:** no findings. The run page shows 7 green stages, an Approved banner, and the extracted-vs-form panel with every *judged* pair matching. No follow-up email is drafted.

**Runtime:** a little longer than before — five extractions instead of three, plus the deliberate per-stage pause.

## EC-2 · Incomplete submission — **PENDING**

Same vendor as EC-1, with three degradations:

1. `incorporation_certificate` **not attached**
2. `address_proof` **not attached**
3. `contact_phone` **blank**

`registered_address` is filled in, so R01 does not report it. Blanking it instead would add a
fourth FIX and change nothing else about the scenario — the field is required like any other; it
is only the *comparison* against the address proof that does not exist.

The PAN card, GST certificate and bank letter are attached and clean, so the run gets all the way
to a decision on the strength of what is missing rather than what is wrong.

**Rules triggered:**

| Rule | Sev | Finding |
|---|---|---|
| R01 | FIX | `Required field 'contact_phone' is missing` |
| R02 | FIX | `Required document 'Certificate of incorporation or business registration' was not attached` |
| R02 | FIX | `Required document 'Address proof' was not attached` |

R12, R17 and R18 stay **silent** — their input documents are absent and R02 already reports that
(skip semantics, `02-data-model.md`). So do R13 and R14, which only ever speak about a document
that is actually there.

**Status:** `PENDING` (3 FIX, 0 BLOCK)

**Expected output — the drafted follow-up:**

> Subject: Additional information needed for your vendor registration (VS-0002)
>
> Hi Priya,
>
> Thanks for submitting your registration for Sundaram Industrial Supplies LLP. Three items need attention before we can complete onboarding:
>
> 1. We did not receive a **certificate of incorporation or business registration**. Please attach it.
> 2. We did not receive an **address proof** — a recent utility bill, lease or bank statement is fine.
> 3. The **contact phone number** was left blank on the form.
>
> Once you send these over we'll pick the review straight back up.

**Why this scenario exists:** it is the **only** one that exercises the brief's *"communicate back what's needed"* requirement, and the only one where a vendor can resubmit. Specific and itemised, not "your submission is incomplete."

## EC-3 · Bank beneficiary mismatch — **REJECTED**

Same vendor as EC-1. All five documents attached, every format valid, every cross-field check passes.

**The one difference:** the bank letter reads `S. Ramesh Kumar`. The submitted `account_holder_name` also reads `S. Ramesh Kumar`, so form and document agree — the form is internally consistent. What it does not match is the **legal entity**.

**Rules triggered:**

| Rule | Sev | Finding |
|---|---|---|
| R09 | **BLOCK** | `Bank account is held in a different name than the vendor entity` · expected `Sundaram Industrial Supplies LLP` · actual `S. Ramesh Kumar` |

Name score is **0.348**, a deterministic MISMATCH well below the 0.75 floor. No model call. Worth pointing out on camera: **the fraud case does not need the AI.**

R10 does **not** fire here — the account number and IFSC on the document match the form; only the *holder* changed. R14 does not fire either: the document is perfectly readable, it just says the wrong name. Both are covered by unit test.

**Status:** `REJECTED`

**Output:** no vendor-facing email. An internal note only.

**Why this scenario exists:** it is the brief's own example (*"the name on the submission doesn't match the name on the bank account"*) and the single most common vendor-payment fraud pattern. **A completeness-only checker approves this and the money is gone.** The sentence for this one is: **complete is not the same as legitimate.**

## EC-4 · Cross-field identity contradiction — **REJECTED**

All five documents present, readable, and in the right slots. All formats valid. Nothing looks wrong on the form.

| Field | Value | |
|---|---|---|
| gstin | `29ABCFS1234K1Z3` | |
| pan | `ABCFS1234Z` | changed |
| entity_type | `Proprietorship` | changed |
| registered_address_state | `Maharashtra` | changed |
| registered_address | `42 Industrial Layout, Koramangala, Bengaluru` | unchanged — a Bengaluru street under a Maharashtra state |

Three edits to the form. The documents are the same clean fixtures EC-1 uses — which is exactly
the point: the vendor did not forge anything, they typed something that the paperwork contradicts.

**Rules triggered:**

| Rule | Sev | Finding |
|---|---|---|
| R06 | **BLOCK** | `GSTIN-embedded PAN does not match the submitted PAN` · expected `ABCFS1234K` · actual `ABCFS1234Z` |
| R07 | **BLOCK** | `PAN encodes entity type 'Firm/LLP' but the submission declares 'Proprietorship'` |
| R15 | **BLOCK** | `The PAN on the card does not match the submitted PAN` · expected `ABCFS1234K` · actual `ABCFS1234Z` |
| R16 | **BLOCK** | `The GSTIN on the certificate belongs to a different PAN than the one submitted` · expected `ABCFS1234K` · actual `ABCFS1234Z` |
| R08 | FIX | `GSTIN is registered in Karnataka (state code 29) but the registered address is in Maharashtra` |
| R18 | FIX | `The address proof is for a different state than the registered address` · expected `Maharashtra` · actual `Karnataka` |

**The unchanged street address is the honest half of this scenario.** The form claims Maharashtra
while the street line still reads Bengaluru, and *nothing in the engine notices that directly* —
`registered_address` is displayed beside the address proof, never compared to it. The state lie is
caught twice anyway, by R08 against the GSTIN's state code and by R18 against the bill, which is
the whole argument for checking the part of an address that has one correct spelling and leaving
the part that does not to a human. Point at the unhighlighted address row on camera: it is a
better answer to *"what doesn't this catch?"* than any slide.

R17 stays **silent**, and that is worth understanding rather than glossing: the form now declares
`Proprietorship`, and a proprietorship has no national registration format, so R17 accepts the
LLPIN on the certificate as a plain registration number. The rule declines to check what it cannot
check — and R07 has already caught the entity-type lie from a completely independent direction.

**Status:** `REJECTED`

**Why this scenario exists:** one changed character in the PAN is contradicted **four separate ways** — by the GSTIN the vendor typed, by the entity type they declared, by the PAN card they uploaded, and by the GST certificate they uploaded — with **zero external API calls**. Add the state, contradicted by both the GSTIN and the electricity bill, and one form yields six findings from four independent directions. It is genuinely invisible to a human reviewer skimming a form, and it is the direct answer to the brief's *"subtle inconsistencies that only become visible when you cross-reference the fields."*

This is the one that makes an interviewer sit up. Build the demo to close on it.
